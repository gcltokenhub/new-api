# 文档治理与 Git 管理规范

- 编号：GOV-TF-001
- 版本：1.0
- 状态：已确认基线
- 日期：2026-09-15
- 适用范围：Token 工厂需求、设计、代码、测试、部署和发布

## 1. 单一事实来源

确认后的仓库文档是开发与验收基线。飞书保留规划与管理沟通，Figma保留视觉设计；仓库记录对应链接、节点、读取日期和已确认结论。

优先级：用户明确决定 → 已批准 PRD/变更记录 → 已批准 ADR/接口/设计文档 → 外部规划与设计参考。来源冲突不私自选择，登记后由相应责任人决定。

## 2. 文档结构

```text
README.md                  项目入口和文档索引
AGENTS.md                  开发协作与代理规则
CHANGELOG.md               用户可感知的版本变化
docs/requirements/         PRD、范围、来源和需求追踪
docs/design/               页面、交互、状态和 Figma 映射
docs/architecture/         系统边界和数据模型
docs/adr/                  技术决策记录
docs/api/                  接口契约和错误码
docs/changes/              已批准需求变更 CR
docs/testing/              验收矩阵、结果和证据索引
docs/deployment/           本地、ECS、备份、恢复和回滚
```

尚无内容的目录在产生第一份受控文档时创建，不提交空占位目录。

## 3. 文档状态与版本

受控文档头部注明编号、版本、状态、日期、责任人及适用代码版本。

状态流转：草案 → 待评审 → 已确认 → 已实现 → 已验收 → 已废弃。状态描述事实；例如写完 PRD 不能标“已实现”，测试环境通过不能标“生产已验收”。

- 小版本：澄清或补充，不改变已批准范围，如 1.1。
- 大版本：范围、关键流程、数据口径或验收标准变化，如 2.0。
- 已废弃文档保留替代文档链接，不删除历史判断。

## 4. 需求与变更追踪

- 需求编号：`TF-001`；待决事项：`Q-01`；变更：`CR-001`；决策：`ADR-001`。
- 每项需求关联来源、页面或接口、任务、实现提交/PR、测试、结果和证据。
- 基线确认后，影响范围、业务规则或验收标准的修改使用 CR，记录原因、影响、决定人、日期和关联需求。
- 数据模型、鉴权边界、计量结算、上游同步及部署架构等长期决策使用 ADR。
- 行为变化必须在同一提交或同一 PR 更新受影响文档。

## 5. Git 仓库与上游

当前目录已有空 Git 仓库，无 commit 和 remote。建立源码基线时：

1. 确认 Token 工厂远程仓库地址及访问策略。
2. 将该仓库设为 `origin`；将确认的 New-API 官方或组织镜像设为 `upstream`。
3. 导入选定 tag 或完整 commit，并在架构/发布文档记录来源、许可证及本地改动起点。
4. 优先保留上游 Git 历史；若业务决定采用快照，必须记录完整上游 commit 和导入方法。
5. 上游升级走独立分支，完成核心调用、权限、额度、日志和迁移回归后合并。

## 6. 分支、提交与评审

- `main` 保存通过当前阶段检查、可形成基线或发布的版本。
- 任务分支：`codex/TF-xxx-short-description`；需求变更：`codex/CR-xxx-short-description`。
- 暂不建立长期 `develop` 分支；需要发布稳定线时再根据实际发布节奏决定。
- 提交信息采用 `type(scope): 描述`，scope 优先使用需求编号，例如 `docs(TF-019): 建立一期需求基线`。
- 一个提交表达一个可审查意图；不要混入本地配置、无关格式化或其他人的修改。
- 合并说明包含关联需求/CR、行为和文档变化、验证证据、迁移/兼容影响及回滚方式。
- 禁止向共享分支强推或改写已共享历史；紧急修复也需留下评审和验证记录。

## 7. 配置、凭证与数据

- 提交依赖锁文件、数据库迁移、配置模板和 `.env.example`，不得提交真实值。
- `.gitignore` 排除 `.env`、密钥、Cookie、日志、本地数据库、备份、构建缓存和运行数据。
- 生产凭证使用部署环境的密钥机制管理；仓库文档只写变量名、用途和获取责任。
- 测试数据使用虚构或脱敏数据。密钥即使撤销也不应保留在 Git 历史中。

## 8. 检查与发布

当前文档阶段最低检查：Markdown 相对链接存在、需求编号与验收矩阵对应、范围与来源无矛盾、`git diff --check` 通过、敏感信息扫描无命中。

源码引入后，在 README/AGENTS 登记准确的格式化、静态检查、单元测试、集成测试、前端构建和端到端命令。只运行文档检查不得声称应用测试通过。

正式版本使用 `v0.1.0` 等语义化 tag。发布记录包含 commit、镜像/产物摘要、依赖与迁移、配置版本、验收结果和回滚条件。数据库回滚必须有迁移或恢复方案，不能只回退应用代码。

## 9. 决策责任

产品负责人确认范围、规则和验收；设计负责人确认交互和视觉；技术负责人确认架构、源码基线及质量门槛；运营/财务确认额度和成本口径；试点负责人完成真实业务验收；发布负责人执行 ECS 发布与回滚。

具体人员未指定前，文档保持“待评审”，不得用角色名称冒充已获得批准。
