## 1. 目标与成功标准

一期定位为集团内部可用版。让一个真实企业下的一个真实项目获得模型服务，完成调用，并让企业管理员看清用量、余额、内部成本、日志和异常。

成功链路：平台创建企业 → 创建项目 → 开通模型 → 分配额度 → 签发项目 API Key → 开发者完成真实调用 → 企业管理员查看结果 → 额度不足或渠道异常时得到提示。

内部试用暂不收费，但计量、内部成本和额度变化必须真实可追溯。验证一个项目是最低验收样本，不允许因此省略租户和项目隔离。

## 2. 范围解释

以飞书 §6.1、§6.4 的阶段一为核心，纳入 §7.1 明确写为一期重点的门户能力。§7.2—7.3 是产品全景，其复杂治理与商业运营功能按 §6 进入后续阶段。

本稿中的“建议规则”与“待决事项”是确认基线中的实施约束：影响交付的待决事项必须在对应设计或开发工作开始前明确。范围、关键规则或验收标准变化须按 [治理规范](../governance.md) 使用 CR 记录。

## 3. 业务对象与最小角色

| 对象 | 定义及边界 |
|---|---|
| 企业租户 | 企业数据、项目、额度和统计的归属边界 |
| 项目 | 属于一个企业的模型调用和成本归集单位 |
| 用户 | 登录主体，通过明确归属访问企业和项目；不能直接假设 New-API 用户就是租户 |
| 模型开通关系 | 项目允许使用哪些模型；门户可见不等于项目已获授权 |
| 上游渠道及 Key | 模型供应方连接与凭证，由平台管理，复用 New-API |
| 项目 API Key | 属于一个项目的调用凭证；多个 Key 的消费仍归集到该项目 |
| Token 用量 | 模型返回或平台核算的输入、输出用量；计量口径须记录 |
| 额度与余额 | 平台批准的使用预算及剩余额度；不默认等同于原始 Token 数 |
| 内部成本 | 外采/自有资源的成本计量，须与免费试用、零收入区分 |
| 调用记录 | 请求的企业、项目、模型、时间、用量、成本和结果；支撑排障和核对 |

一期建议保留平台管理员、企业管理员、项目开发者三个固定角色，不增加可配置权限引擎。角色分配方式待确认。

| 操作 | 平台管理员 | 企业管理员 | 项目开发者 |
|---|---|---|---|
| 企业开户、渠道及上游凭证管理 | 允许 | 不允许 | 不允许 |
| 企业/项目视图 | 按平台职责 | 仅本企业 | 仅授权项目 |
| 项目创建、模型开通、额度分配 | 允许；具体分工待确认 | 候选：本企业范围 | 不允许 |
| 项目 Key 管理及调用 | 按管理职责 | 本企业授权范围 | 仅授权项目；Key 管理权限待确认 |
| 用量、成本、日志 | 按平台职责 | 仅本企业 | 项目日志可见；内部成本可见性待确认 |

跨租户或项目的数据访问应在后端校验，不能依赖前端隐藏菜单。

## 5. 一期不默认包含

- **二期方向**：完整成员组织、动态角色权限、申请审批流、额度回收/冻结、成本中心、正式账单与对账、完整操作审计后台。
- **三期方向**：在线充值支付、复杂价格套餐、合同和结算、收入毛利分析、客户全生命周期管理、客户支持系统、定制路由运营。
- **暂缓**：公开 Token 交易撮合、复杂商城、大量低频模型、图像/视频体验、模型对比、GPU 资源编排与租赁交付、缺乏依据的海外节点服务承诺。

基础身份隔离、必要额度变更记录、请求追踪及现有 New-API 限流仍属于一期。上面的“完整审计”“额度台账”“路由运营”是后续产品化深度，不取消一期正确性要求。

## 6. 待评审的业务规则

1. **开户与登录**：建议平台为内部试点开户并指定企业管理员；接入申请不自动创建企业或授予额度。不默认开放公众自助注册。
2. **模型授权**：模型目录与可用渠道分开维护；项目必须显式开通后才可调用。
3. **额度**：建议项目共享一份预算，所有项目 Key 消费归集于该预算，避免按 Key 重复发放。单位、倍率、精度及并发扣减由 Q-02 决定。
4. **成本**：记录计量数据与调用时适用的成本规则版本；价格变化不能悄然改写历史成本。若上游未返回用量，标记未知/待核算而非默认为零。
5. **失败与流式中断**：区分未发送上游、上游拒绝、超时、部分流式返回和已消耗但结算未完成；不能简单规定“所有失败都免费”。按批准的上游及平台口径核算。
6. **API Key**：归属项目，停用后拒绝新请求；明文展示/找回策略、有效期与默认限制待确认。上游 Key 永不返回普通用户。
7. **模型体验**：建议登录后选择授权项目及模型；体验和 API 共享项目预算。限流、超时、额度不足和上游失败应有可理解的状态。
8. **接入申请**：建议一期为提交 → 平台查看 → 人工跟进，去重/防刷并限制联系人访问；不建设多级审批和自动商务流。
9. **基础告警**：建议站内提示与告警列表作为第一版；外部通知渠道、阈值、合并频率与恢复状态待 Q-05 确定。
10. **内容真实性**：首页模型能力、价格、算力指标和服务承诺须有维护责任人及来源；未核实信息在上线前调整，不把设计静态数值冒充实时数据。

## 7. 后端复用原则与技术工作边界

优先沿用 New-API 核心模型接入、上游 key 池、请求转发、限流、用户认证、令牌及基础日志。企业、项目、模型开通、额度归属、内部成本视图和接入申请由 Token 工厂产品层定义。

推荐先核对 New-API 的已有模型/接口，再决定必要的映射或扩展；“少量接口扩展”是控制改动的目标，尚不能承诺企业项目层无需数据模型变更。不得在缺乏验证时用用户/分组映射替代租户隔离。

实施前比较：A. 原界面换肤（不能完整覆盖企业项目闭环）；B. 复用核心并增加薄业务层（推荐评估）；C. 独立重建完整网关（当前范围不需要）。本稿不锁定前端框架或新增接口路径。

## 8. 非功能与交付条件

- 访问控制：企业及项目边界在 API 强制执行，默认拒绝未授权访问。
- 数据正确性：用量、额度和成本可以对账；超时、重试、并发和重复结算有明确口径及测试。
- 可观测性：能从请求追踪到项目、模型、渠道及结果；敏感凭证脱敏，内容日志保存策略待确认。
- UI：以已提供桌面 Figma 首页作为视觉依据；其他页面与移动端适配范围另列设计缺口。
- 环境：开发、测试、生产配置隔离；部署不依赖个人机器上的未记录操作。
- 性能：并发、时延、统计刷新周期、数据保留期限及恢复目标待定，不凭空写入 SLA 数值。
- 上线：完成首个真实项目验收；生产密钥、数据库、域名/TLS、备份恢复及发布责任落实后进入 ECS 部署。
